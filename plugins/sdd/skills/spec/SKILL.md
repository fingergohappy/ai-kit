# /spec: 写实施 spec

spec 回答 "改哪里, 按什么顺序改, 怎么测, 怎么上线". 它不重写业务规则 (那在 REQ, 按条目号引用),
只回答实现问题. 写它的过程分两半, 顺序不能颠倒:

1. **侦察**: 把 "我以为代码是这样" 换成 "代码在 file:line 就是这样". 这是整份文档的发动机.
2. **计划**: 每一条改动都能追到某条侦察结论.

先写计划再补侦察, 出来的就是想象中的系统. AI 最不可靠的恰恰是对现状的判断, 所以这个顺序是硬的.

## 步骤

1. **定位与状态**. 找到 `../sdd/scripts/sdd.py`, 读约定 `../sdd/references/conventions.md`.
   `sdd.py status CR-NNN` 确认: CR 存在, `01-docs` review 已 fixed (没审过就先 `/review-cr CR-NNN docs`,
   软闸门, 用户明说跳过才继续), spec 还不存在 (已存在就是要改它, 见下面 "已有 spec 时").
   没给 CR 编号: 会话里提过就用那个, 只有一个未 fixed 的 CR 就用它, 否则列出来问.

2. **读上游**. 从磁盘重读 CR 全文与它 affects 的每份 REQ (会话里的版本可能已经变了), 以及
   `notcommit/CR-NNN-*/draft/` 里的草稿 -- `/draft` 与 `/req` 阶段的侦察结论在那里, 别重复劳动.
   再读 `docs/sdd/lessons.md` (有的话): 次数 >= 2 的条目是这个仓库反复踩的坑, 写计划时就避开,
   比等到 impl review 被抓出来便宜.

3. **建文件**: `sdd.py new-spec CR-NNN`. 基点 commit 由脚本填进 frontmatter 的 `base`,
   §1 的所有 file:line 都相对它成立.

4. **§1 代码侦察结论 -- 先写完这一节, 再写别的**. 每条三段式:

   > **事实** (带 file:line) -> **推论** (由此会发生什么) -> **对改动的约束** (所以必须怎么改)

   要核实的类别 (模板注释里也有, 逐类过一遍, 不适用的跳过):

   | 类别 | 具体问什么 |
   |---|---|
   | 唯一入口 | 这个判定 / 状态迁移只有一个地方做吗? 有没有第二个调用点? |
   | 约束与守卫 | CHECK, 触发器, 唯一键, NOT NULL -- 新形态会不会被现有约束拒绝? |
   | 幂等与锁 | 幂等键的范围是什么? 锁是连接级还是事务级? 两条循环之间有没有缝? |
   | 队列 | claim 的进入条件是什么? 新形态会不会让某行既不能取又不能放, 堵住队首? |
   | 配置 | 有没有同类开关的先例可抄 (默认值, 依赖关系, 校验位置)? |
   | 迁移 | 当前最大编号? 配套守卫 (lock, DBML, 迁移测试) 是什么? |
   | 测试 | 同类测试的夹具在哪? 真库还是单元? |

   侦察出与 CR / REQ 描述不符的事实 (文档说 A, 代码是 B): **立刻告诉用户**, 记进 §0 口径演化或 §9.
   这时候纠正比写完代码再纠正便宜一个数量级 -- 这是写 spec 最大的价值之一.

5. **§2 - §8 计划**. 每节的写法在模板注释里, 重点:

   - **§2 改动总览**: 按包一行, 并写 "明确不改" -- 反向核实一遍: 改 X 会不会迫使改 Y?
   - **§3 数据与迁移**: down 在有审计行时是否该拒绝; 能否先行独立合并 (零行为变化).
   - **§4 分步**: 每步的约束是 **合并后系统仍然正确** -- 迁移先行且零行为变化, 开关默认关时全路径
     等价, 切流单独一步. 落点列全填 `待办`, 由 `/implement-cr` 填提交 hash. 保持四列表头,
     `sdd.py status` 靠它算进度.
   - **§5 测试**: T1..Tn 覆盖 CR 变更内容表的**每条 AC**; 写清真库还是单元, 夹具在哪; 并发 / 幂等
     断言写明用几个连接 (同一事务里第二次锁是空操作, 测不出跨连接互斥); 迁移往返也算一条.
   - **§6 风险与回退**: 每条 "风险 -> 缓解 / 回退动作"; 回退是开关还是迁移 down, 会不会销毁数据.
   - **§7 明确不做**: 带理由或去向. 这一节对实施者的约束力仅次于 §1 -- 顺手多改是最常见的越界.
   - **§8 上线检查单**: 逐项可执行 (工单, 关闭条件, 责任人, 部署不变量, 盘点查询).
   - **§9 留空**, 由 `/implement-cr` 边做边填.

6. **自检**: CR 的每条 AC 在 §5 有对应的 T 吗? §2 的每处改动能追到 §1 的某条结论吗?
   §4 每一步单独合并后系统还正确吗? 有一项答不上就补, 别留给 review.

7. **收尾**: 报文件路径, §1 条数, §4 步数, §5 用例数, 以及侦察中发现的与文档不符之处.
   下一步 `/review-cr CR-NNN spec`.

## 已有 spec 时

改而不是重写: 保留 §1 已核实的结论 (除非它被证伪 -- 那要改并说明), 在 §9 记下这次改了什么、为什么.
`sdd.py new-spec CR-NNN --force` 会覆盖整份, 只在确实要推倒重来时用.

## 不做

- **不写、不改项目代码**. 只读侦察, 跑只读命令. 实施是 `/implement-cr` 的事 -- 这条边界让用户可以
  只要方案不要改动.
- 不在 spec 里重写业务规则. 需要引用就写 "REQ-006 FR-5", 不抄正文.
- §1 不写没核实的话. 拿不准就标 "未核实" 并列进 §9 或开放问题, 不要用推测填满侦察节.
- 不跳过 `01-docs` review 直接写 spec, 除非用户明说 -- 文档层面的错会被原样翻译成实施计划.
