# /auto-cr: 无人值守推进一个 CR

不是新流程, 是同一条流程的无人值守模式: 每一步仍然照那一步的 SKILL 做 (`/review-cr` 就读
`../review-cr/SKILL.md` 按它的七步做), 区别只有三点 -- 不逐步问用户, review 并行外包, 歧义记成 OQ 往下走.

**推到哪为止**: 落实那一步之前停 (`/implement-cr` 的落实段, 它会把 REQ 置 implemented). 因为
REQ 第 10 节的开放问题必须在 implemented 前清空, 而自动推进期间攒下的 OQ 只有用户能拍板.
所以终点是 "代码就绪 + impl review 已 fixed + OQ 清单待确认", 最后一公里留给人.

## 前提

1. `sdd.py status CR-NNN` 能查到这个 CR, 且状态不是 `fixed` / `rejected`.
2. 工作树干净 (`git status --porcelain` 为空) -- 自动推进会连续提交, 混着别人的改动没法回退.
3. 并行 review 要在 tmux 里跑 (`$TMUX` 非空) 且 `codex` / `pi` 至少有一个在 PATH 上.
   不满足就降级成串行自审, 在开场白里说明, **不要**因此中止.
   用户给了 `--serial` 也走串行.

任一条不满足且无法降级 (比如 CR 不存在, 工作树脏), 停下来说清楚, 不要猜.

## 主循环

```
读 sdd.py status CR-NNN 的 "下一步"  ->  按下表做  ->  再读一次
```

每轮开始都重新读状态, 不要凭记忆推进 -- 状态在文件里, 上一步可能没落盘成功.

| status 给的下一步 | 自动模式怎么做 |
|---|---|
| `/review-cr CR-NNN docs\|spec\|impl` | **并行外包**, 见下一节 |
| `/review-cr CR-NNN <stage>` (复核模式) | 自己做, 照 review-cr SKILL 第 6 步 |
| `/spec CR-NNN` | 自己写 (串行: spec 是一份连贯文档, 拆开写会互相矛盾) |
| `/implement-cr CR-NNN` (处理发现) | 自己做, 逐条处置 |
| `/implement-cr CR-NNN` (分步实施) | 自己做, TDD, 每步一提交 |
| `/implement-cr CR-NNN` (落实) | **停** -- 到终点了, 出 OQ 清单 |
| `/review-cr CR-NNN distill` | **停** -- distill 要问用户删哪些文件 |

只有 review 外包, 写的活自己干. 写的活并行需要 worktree 隔离, 而 spec 与分步实施本来就是串行依赖,
拆开只会制造冲突.

## 并行 review

照 `agent-crew` 的 review 形状做: **一个车道一个窗口**, 审完 kill 掉.

**1. 定窗口数**: 按 `../sdd/references/review-lanes.md` 里**该阶段**那张表, 逐条车道判断对本 CR 适不适用,
适用的各起一个窗口. 所以窗口数是 1 到 5 个 (每阶段车道表 A-E 五条), 由 CR 的性质决定, 不是固定两个.

车道表是唯一的切分依据: 不要自己发明角度, 也不要为了省窗口把两个车道塞给同一个 agent, 更不要
把一个车道拆给两个 agent -- 同一个角度审两遍只会产生两份重复发现, 还要你去合.

不适用的车道不开窗口, 但要在合并后的 review 的车道结论表里写明 "C 算术与不变量: 本 CR 不涉及金额计算,
未审". 没开的窗口和审过没发现是两回事, 分不清就等于没审.

**2. 起窗口** (每阶段新起, 不复用 -- 上一阶段的上下文会污染这一阶段的结论):

```sh
tmux has-session -t agents 2>/dev/null || tmux new-session -d -s agents
# 一个车道一个窗口, 窗口名带车道号, 便于 tmux list-windows 一眼看出谁在审什么
tmux new-window -t agents -n codex-CR-NNN-<stage>-A "cd <repo 绝对路径> && exec codex -m gpt-5.6-sol -c model_reasoning_effort=\"max\""
tmux new-window -t agents -n pi-CR-NNN-<stage>-B    "cd <repo 绝对路径> && exec pi --provider xai --model grok-4.6 --thinking xhigh"
tmux list-panes -t agents:codex-CR-NNN-<stage>-A -F '#{pane_id}'
```

模型 id 照抄, 不要缩写 -- 写错了窗口会停在 shell 提示符上, 看起来跟 "正在思考" 一模一样.

**模型分配**: 车道之间交替换工具, 别让所有车道都用同一个模型 -- 同一个盲点审五遍还是那个盲点.
要跑代码 / 跑测试的车道 (docs A, spec A, impl A / B / E) 优先给手上更强的那个.
只有一个工具可用时全给它, 车道照样一个一个开.

**3. 派发**: 用 `tmux-dispatch` skill 送 brief, 一个窗口一份, 不要自己 `send-keys`. 每份 brief 必须自带:

- 审什么: CR / REQ / spec 的**绝对路径**, impl 阶段另给基点 commit 与 `git diff` 范围
- 审哪个车道: 车道名 + review-lanes.md 里那一行原文 (对方读不到你的上下文), 并写明
  **只审这一个车道**, 别的角度留给别的窗口
- 错题本: `docs/sdd/lessons.md` 的绝对路径, 本车道且次数 >= 2 的行当硬性检查项
- 写哪里: `notcommit/CR-NNN-<slug>/reviews/0N-<stage>-<车道字母>.md` -- 按车道命名, 一个窗口一个文件,
  绝不让两个窗口写同一个文件. 格式照 `../sdd/assets/templates/review.md`, 发现编号在自己文件里从 1 编起
- 边界: **只读, 不改任何代码与文档**
- 完成线: 本车道结论 + 发现表填完, 每条发现带 file:line 或条目号与最小修复

**4. 收**: **所有**窗口都 `DONE:` 之后再合并. 少任何一个都不要开始合 -- 一个窗口没产出不等于
它没发现问题, 等于它没跑成. 缺谁就看那个窗口的 pane, 报出来, 别拿部分结果当全份.

**5. 合并**成 `reviews/0N-<stage>.md` (这才是 sdd.py 认的文件名):

- 车道结论表逐条填: 开了窗口的填该窗口的结论, 没开的填 "未审" 加理由
- 发现表按 `D-`/`S-`/`I-` **重新连续编号**, 各车道文件里的编号丢掉 (它们马上要删)
- 车道之间本来就不该重叠, 真出现同一问题两条 -> 合成一条, 保留更具体的那句, 级别取高的
- 结论冲突 -> 保留最严的, 在发现栏注明分歧 (照 review-cr SKILL 第 4 步)
- 整体 verdict 取所有车道里最严的: 一个 BLOCK 就是 BLOCK
- 合并完删掉 `0N-<stage>-<车道>.md` 中间文件, kill 这一轮的全部窗口

## 轮次上限

**一轮 = 一次完整往返**: 这一轮的窗口全部派出去, **全部**回来, 合并成一份 review. 派出去一个 agent
不算一轮, 全部回来才算 -- 否则拿部分结果就把轮次耗掉了. 一轮里开几个窗口不影响计数,
开五个和开两个都是一轮.

首审是第 1 轮; 处置完发现后的每次复核各占一轮.

| 阶段 | 审的是 | 上限 |
|---|---|---|
| docs | 文档 (CR + REQ delta) | **2 轮** |
| spec | 文档 (实施计划) | **2 轮** |
| impl | 代码 | **3 轮** |

文档给 2 轮, 代码给 3 轮, 差别不是随意定的: 文档的问题是可穷尽的 (条目对不对得上, 现状说得对不对),
两轮还收敛不了说明 CR 或 spec 本身结构有问题, 该由人重写而不是继续磨; 代码的修复会带出新问题,
所以多给一轮.

到上限仍未 `fixed` 就停, 不要开第 3 / 第 4 轮. 停下来时把该阶段剩下的未处置发现原样列给用户 --
连续几轮收敛不了的发现, 通常是自动推进判断不了的那一类.

## 歧义: 先做, 记 OQ, 往下走

分两类, 处理方式不同:

**技术歧义** (用哪个实现, 分几步, 表怎么建) -- 自己定, 理由写进 spec 第 6 节替代方案或 CR 第 4 节.
不记 OQ, 这本来就是 spec 该决定的事.

**业务歧义** (规则没定, 边界没说, 两种读法都说得通, 会改变验收标准) -- 按自己推荐的做法执行,
同时在受影响 REQ 的第 10 节追一条:

```markdown
- **OQ-1** (CR-005 自动推进 2026-08-31): 退款超过原单金额时是拒绝还是按原额封顶?
  **已按**: 拒绝并返回 422. **理由**: 与 REQ-003 BR-7 的超付防线一致, 封顶会静默改写用户意图.
  **影响**: 若改判为封顶, 要动 FR-4 / AC-6 与 `refund.go` 的校验分支.
```

四段缺一不可 -- 没有 "影响" 那段, 用户没法判断改判的代价, OQ 就变成了没人敢碰的悬案.

**不能自己拍板, 必须当场停下**的: 要动 CR 影响范围之外的 REQ 条目; 要改已 fixed 的 review 的结论;
要跳过某次 review; 迁移会销毁审计数据. 这几样越权的代价不对称, 记 OQ 往下走等于把错误做实了.

## 停止条件

到了就停, 汇报, 不要自己往下闯:

1. **到终点** -- 下一步是落实
2. **review 出 P0 且最小修复超出 CR 范围** -- 记 OQ 不够, 这要改 CR 本身
3. **测试跑不过且两次修复都没解决** -- 别第三次改测试去迁就实现
4. **越权项** (见上一节最后一段)
5. **外包窗口都失败** 且串行自审也做不了
6. **某阶段 review 到了轮次上限仍未 fixed** (docs / spec 2 轮, impl 3 轮)

停的时候说清楚: 停在哪一步, 为什么, 已经做完了什么 (提交列表), 用户拍板后怎么继续.

## 汇报

跑完或停下都出这四样:

1. **走了哪几步**: 每步一行, 带产出 (提交 hash / 文件路径)
2. **review 结果**: 每阶段的 verdict, **用了几轮 (上限几轮)**, P0 条数, 哪些窗口跑了哪些车道
3. **OQ 清单**: 逐条列出问题 + 已按什么做 + 改判要动什么 -- 这是用户唯一必须逐条看的东西
4. **下一步**: 通常是 "确认 OQ 后 `/implement-cr CR-NNN` 落实"

OQ 一条都没有时明说 "无 OQ", 别省略这一节 -- 用户要能区分 "没有歧义" 和 "忘了记".

## 不做

- 不落实 REQ, 不置 CR fixed (OQ 没确认之前 REQ 不能 implemented)
- 不 distill, 不删任何工作目录文件 (那一步要问用户)
- 不 push, 不开 PR, 不合并分支
- 不并行写代码 (只并行 review)
- 不改 `../sdd/references/` 下的约定去迁就当前这个 CR
