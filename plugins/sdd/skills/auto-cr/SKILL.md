# /auto-cr: 无人值守推进一个 CR

不是新流程, 是同一条流程的无人值守模式: 每一步仍然照那一步的 SKILL 做 (`/review-cr` 就读
`../review-cr/SKILL.md` 按它的七步做), 区别只有三点 -- 不逐步问用户, review 并行外包, 歧义记成 OQ 往下走.

**推到哪为止**: 落实那一步之前停 (`/implement-cr` 的落实段, 它会把 REQ 置 implemented). 因为
REQ 第 10 节的开放问题必须在 implemented 前清空, 而自动推进期间攒下的 OQ 只有用户能拍板.
所以终点是 "代码就绪 + impl review 已 fixed + OQ 清单待确认", 最后一公里留给人.

## 前提

开工前读约定 `../sdd/references/conventions.md` (六个命令共用的那份, 自动模式一样受它约束:
提交粒度, 每推进一步贴进度, 压缩提交的边界). 不逐步问用户不等于不守约定.

1. `sdd.py status CR-NNN` 能查到这个 CR, 且状态不是 `fixed` / `rejected`.
2. 工作树干净 (`git status --porcelain` 为空) -- 自动推进会连续提交, 混着别人的改动没法回退.
3. 并行 review 要在 tmux 里跑 (`$TMUX` 非空) 且 `codex` / `pi` 至少有一个在 PATH 上.
   不满足就降级成串行自审, 在开场白里说明, **不要**因此中止.
   用户给了 `--serial` 也走串行.

任一条不满足且无法降级 (比如 CR 不存在, 工作树脏), 停下来说清楚, 不要猜.

## 主循环

```
读 sdd.py status CR-NNN 的 "下一步"  ->  按下表做  ->  再读一次
```

每轮开始都重新读状态, 不要凭记忆推进 -- 状态在文件里, 上一步可能没落盘成功.

`status CR-NNN` 开头那张八关进度表就是这一轮的自检: 上一轮做完的关应该已经变 ✓, 没变就是没落盘,
回去看那一关的文件而不是接着往下走. 汇报 "走了哪几步" 时也照它写, 别照记忆写.

| status 给的下一步 | 自动模式怎么做 |
|---|---|
| `/review-cr CR-NNN docs\|spec\|impl` | **并行外包**, 见下一节 |
| `/review-cr CR-NNN <stage>` (复核模式) | 自己做, 照 review-cr SKILL 第 6 步 |
| `/spec CR-NNN` | 自己写 (串行: spec 是一份连贯文档, 拆开写会互相矛盾) |
| `/implement-cr CR-NNN` (处理发现) | 自己做, 逐条处置 |
| `/implement-cr CR-NNN` (分步实施) | 自己做, TDD, 提交可跨回退单元一体的连续几步 |
| `/implement-cr CR-NNN` (落实) | **停** -- 到终点了, 出 OQ 清单 |
| `/review-cr CR-NNN distill` | **停** -- distill 要问用户删哪些文件 |

只有 review 外包, 写的活自己干. 写的活并行需要 worktree 隔离, 而 spec 与分步实施本来就是串行依赖,
拆开只会制造冲突.

## 并行 review

照 `../review-cr/SKILL.md` 的 `## 并行审` 那节做, 五步一模一样: 定窗口数 (车道表) / 起窗口 /
用 `tmux-dispatch` 派 brief / 全部 `DONE:` 才收 / 合并成 `reviews/0N-<stage>.md`.

自动模式只差一条: **不问用户要不要并行**. 前提第 3 条满足就直接并行, 不满足降级串行自审并在
开场白说明, `--serial` 同样走串行. 那节里 "问一次就够" 的那段对无人值守不适用 -- 没人可问.

## 轮次上限

**一轮 = 一次完整的 "审 -> 处置 -> 复核"**: 派出去的窗口**全部**回来, 合并成一份 review,
照 `/implement-cr` 逐条处置, 再复核. 复核通过置 `fixed`, 这一轮就完了, 直接进下一阶段.

**审出发现不等于停**. 发现就是拿来修的 -- 处置和复核都在同一轮里, 不要修完就回头问用户
"要不要复核". 只有复核**打回**时 (没真修好, 或修复带出新问题) 才开始下一轮, 重新审一遍.

派出去一个 agent 不算一轮, 全部回来才算 -- 否则拿部分结果就把轮次耗掉了. 一轮里开几个窗口
不影响计数, 开五个和开两个都是一轮.

| 阶段 | 审的是 | 上限 |
|---|---|---|
| docs | 文档 (CR + REQ delta) | **1 轮** |
| spec | 文档 (实施计划) | **1 轮** |
| impl | 代码 | **2 轮** |

文档给 1 轮, 代码给 2 轮, 差别不是随意定的: 文档的问题是可穷尽的 (条目对不对得上, 现状说得对不对),
一轮审出来的东西处置掉就该往下走; 首审就暴露的结构性问题 (CR 或 spec 本身写歪了) 不是多审几遍
能磨平的, 该停下来让人重写. 代码的修复会带出新问题, 所以多给一轮复核.

到上限仍未 `fixed` 就停, 不要多开一轮. 停下来时把该阶段剩下的未处置发现原样列给用户 --
连续几轮收敛不了的发现, 通常是自动推进判断不了的那一类.

所以文档阶段 1 轮的实际含义是: **审一次, 修一次, 复核一次, 过了就走** -- 正常路径全在这一轮里.
只有复核打回才触碰上限: 那说明处置没解决问题, 而文档的问题连修一次都收不敛, 多审一遍也是白审,
该停下来让人看. 代码给 2 轮, 是因为修复常带出新问题, 允许打回一次再修.

## 歧义: 先做, 记 OQ, 往下走

哪些算业务决策, 什么时候该问什么时候记 OQ, 见 `../sdd/references/conventions.md` 的
`## 业务决策: 谁拍板, 什么时候问`. 自动模式永远落在 "记 OQ 往下走" 那一档 -- 无人可问.

两个容易记混的:

- **技术歧义** (用哪个实现, 分几步, 表怎么建) 不记 OQ, 自己定, 理由写进 spec 第 6 节或 CR 第 4 节.
- **CR 里已经和用户确认过的业务决策** 也不记 OQ -- 照做即可, 它早就不是开放问题了.
  review 若与它冲突, 以 CR 为准 (处置写 `不采纳: CR 第 N 节已确认 ...`).

真正要记 OQ 的是**没定过**的业务歧义: 按自己推荐的做法执行, 同时在受影响 REQ 的第 10 节追一条:

```markdown
- **OQ-1** (CR-005 自动推进 2026-08-31): 退款超过原单金额时是拒绝还是按原额封顶?
  **已按**: 拒绝并返回 422. **理由**: 与 REQ-003 BR-7 的超付防线一致, 封顶会静默改写用户意图.
  **影响**: 若改判为封顶, 要动 FR-4 / AC-6 与 `refund.go` 的校验分支.
```

四段缺一不可 -- 没有 "影响" 那段, 用户没法判断改判的代价, OQ 就变成了没人敢碰的悬案.

**不能自己拍板, 必须当场停下**的四项越权 (动范围外的 REQ 条目 / 改已 fixed 的 review 结论 /
跳过某次 review / 迁移销毁审计数据) 见 conventions 那节. 代价不对称, 记 OQ 往下走等于把错误做实.

## 停止条件

到了就停, 汇报, 不要自己往下闯:

1. **到终点** -- 下一步是落实
2. **review 出 P0 且最小修复超出 CR 范围** -- 记 OQ 不够, 这要改 CR 本身
3. **测试跑不过且两次修复都没解决** -- 别第三次改测试去迁就实现
4. **越权项** (见上一节最后一段)
5. **外包窗口都失败** 且串行自审也做不了
6. **某阶段 review 到了轮次上限仍未 fixed** (docs / spec 1 轮, impl 2 轮)

停的时候说清楚: 停在哪一步, 为什么, 已经做完了什么 (提交列表), 用户拍板后怎么继续.

## 汇报

**每轮贴一次进度**: 主循环每轮都用 `status CR-NNN --write` 读, 把进度表贴出来, 同时它落进
`PROGRESS.md` -- 无人值守时用户就靠那个文件旁观 (完整约定在
`../sdd/references/conventions.md` 的 `## 每推进一步就贴进度`).
无人值守时用户不在旁边看, 这串进度表是他事后复原你走过哪些关的唯一凭据 -- 攒到最后一起讲等于没有.

跑完或停下再出这四样:

1. **走了哪几步**: 每步一行, 带产出 (提交 hash / 文件路径)
2. **review 结果**: 每阶段的 verdict, **用了几轮 (上限几轮)**, P0 条数, 哪些窗口跑了哪些车道
3. **OQ 清单**: 逐条列出问题 + 已按什么做 + 改判要动什么 -- 这是用户唯一必须逐条看的东西
4. **下一步**: 通常是 "确认 OQ 后 `/implement-cr CR-NNN` 落实"

OQ 一条都没有时明说 "无 OQ", 别省略这一节 -- 用户要能区分 "没有歧义" 和 "忘了记".

## 不做

- 不落实 REQ, 不置 CR fixed (OQ 没确认之前 REQ 不能 implemented)
- 不 distill, 不删任何工作目录文件 (那一步要问用户)
- 不 push, 不开 PR, 不合并分支
- 不并行写代码 (只并行 review)
- 不改 `../sdd/references/` 下的约定去迁就当前这个 CR
