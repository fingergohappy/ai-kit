# 三次 review 各查什么

review 的产出是 `reviews/0N-<stage>.md` (模板 `assets/templates/review.md`). 每次 review 按
车道 (lane) 组织; 一个车道一个视角, 各出一个结论 (BLOCK / OK with notes / OK), 整体结论取
最严的那个. 车道可以拆给不同的代理或模型并行跑, 结果汇总进同一个文件.

通用要求, 三次都适用:

- **每条发现可复现或可核对**: 位置 file:line (或 REQ / CR 条目号), 证据 (代码怎么写的,
  与哪条 AC / BR 冲突), P0 附步骤. 没证据的怀疑降为 P2 并注明 "未核实".
- **最小修复要具体**: 给改法 (SQL 片段, 条件表达式, 该加的断言), 不写 "考虑改进".
- **对照物是文档不是记忆**: 从磁盘重读 CR / REQ / spec, 会话里看过的版本可能已经变了.
- **宁可漏报不误报 P0**: P0 的含义是 "不修不能合并", 拿不准就 P1 并说明不确定在哪.
- **没发现也出文件**: 状态直接 fixed, 结论 OK. 否则分不清 "审过没问题" 和 "没审".
- **先读错题本**: `docs/sdd/lessons.md` 里本阶段车道的行是这个仓库真犯过的错; 次数 >= 2 的必查, 命中时在
  发现栏写 "命中 L-n" (提炼时据此累加次数).

---

## 01 docs: 审 CR + REQ delta (写 spec 之前)

对象: `cr/CR-NNN-*.md`, 影响需求列出的每份 REQ, `notcommit/CR-NNN-*/draft/` 里的草稿.

| 车道 | 要问的问题 |
|---|---|
| A 代码事实 | CR 动机与现状描述里的每个 "现在系统是 X" 是否属实? 逐条对代码核实, 给 file:line. 文档写错现状是后面一切错误的源头. |
| B 条目对齐 | **变更 CR**: 影响需求的条目号在 REQ 里存在吗? 变更内容表每一行的 "现行" 与 REQ 正文一字不差吗? FR 改了, 对应 AC 有没有跟着改? 新增 FR 带 AC 了吗? 删除给了原因与存量处置吗? **立项 CR**: 交付范围列出的条目在 REQ 里都存在吗? REQ 里有没有本期不做却没标注的编号条目 (与 implemented 矛盾)? 每条 FR 都有 AC 吗? |
| C 算术与不变量 | 公式, 取整方向, 单位 (minor / major), 精度, 边界值 (0, 最大值, 退化配置) 算一遍. 用具体数字验一个算例. 资金类文档的错误多数出在这里. |
| D 设计缺口 | 状态机有没有画不出来的迁移 (中间态 + 重放, 开关翻转, 并发两连接)? 幂等键范围? 未知结果怎么收敛? 队列会不会堵队首? 回滚会不会销毁审计记录? |
| E 范围 | 非目标写清了吗? "不做 X" 有理由或去向吗? 有没有把实现细节 (表, 字段, 函数名) 写进 FR / BR? 有没有把论证 (推导, 复现) 写进 REQ 正文而不是留在 review? **立项 CR 另查**: 第 3 节 "对现有系统的影响" 是靠侦察得来还是靠推测 -- 逐条核实它说的依赖 / 冲突 / 争用是否属实, 以及有没有漏的 (共享表约束, 同一把锁, 幂等键空间, 路由冲突, 开关回退路径). 这是新业务最常见的翻车点. |

产出的发现编号 `D-1, D-2, ...`.

## 02 spec: 审实施计划 (写代码之前)

对象: `notcommit/CR-NNN-*/spec.md`, 对照 CR 与 REQ.

| 车道 | 要问的问题 |
|---|---|
| A 侦察核实 | §1 每条 file:line 在基点 commit 上是否成立? 结论是否被断章取义 (只看了一个调用点, 其实有两个)? 有没有该侦察而没侦察的: 约束 / 触发器, 队列进入条件, 锁的范围, 配置阶梯先例, 迁移号. |
| B 分步 | §4 每步合并后系统仍正确吗? 迁移先行是否零行为变化? 开关默认关时全路径等价吗? 切流是不是单独一步? 两步之间有没有隐藏依赖 (步 5 依赖步 0 的门槛)? 制品拆分 (代码 + schema 一批, 切流迁移另一批) 有没有考虑发布流程 (migrate 先于滚动容器)? |
| C 测试覆盖 | CR 变更内容表里每条 AC 在 §5 有对应 T 吗? 并发 / 幂等断言是两个连接还是同一事务? 中间态重放 (两个方向) 有用例吗? 迁移往返 (up -> down -> up) 有吗? 负例 (非法配置被拒, NULL 语义) 有吗? |
| D 数据与回退 | down 在有审计行时是否拒绝? 回填规则? 新旧代码并跑窗口的数据形态兼容? 回退动作是开关还是迁移, 回退会不会丢数据? |
| E 范围 | §7 明确不做是否覆盖了容易顺手改的东西? §2 "明确不改" 的包是否真的不需要改 (反向核实: 改 X 会不会迫使改 Y)? |

产出的发现编号 `S-1, S-2, ...`.

## 03 impl: 审实现 (落实 REQ 之前)

对象: 代码 diff (基点 -> 当前), 对照 spec 与 CR 的 AC. 借 OpenSpec verify 的三个维度
(完整 / 正确 / 一致) 再加资金系统必需的两条.

| 车道 | 要问的问题 |
|---|---|
| A 完整性 | spec §4 每步有落点 (提交 hash) 吗? CR 每条 AC 有测试且通过吗 (跑一遍, 不看声明)? spec §5 每条 T 存在吗? §9 记了偏差吗? REQ 更新与代码同分支吗? |
| B 正确性 / 金融安全 | 超付: 同一份余额能不能被答应两次 (快照与在途的时间窗)? 幂等: 键的范围与重放路径? 并发: 锁是连接级还是事务级, 两条循环之间有没有缝? 未知结果: 只读收敛还是重发? 取整方向对谁不利? 拿 spec §1 的事实逐条对照实现. |
| C 安全 / 合规 | 2FA / step-up 有没有被绕过的路径? 审计: 强制动作是否落库且与政策动作可区分? 权限: 谁能改热配置, 改了留痕吗? 日志会不会泄露敏感字段? |
| D 代码质量 / 一致性 | 遵循 spec 决定了吗 (spec 说不加守卫, 代码加了没)? 与仓库既有模式一致 (错误码, 事件常量, 查询文件位置)? 死代码, 重复, 顺手改了 §7 说不改的东西? |
| E 测试质量 | 断言到点了吗 (T11 同一事务测不出跨连接锁)? 夹具是真库还是 mock 了存储层 (仓库惯例真库)? 有没有 "测试通过但没测到 AC" 的用例? |

产出的发现编号 `I-1, I-2, ...`. 测试缺口表必填.

## 复审 (rereview)

发现被处置后, 复审在**同一文件**填 "复核" 列: "已核 <日期>" 或 "未修复: <说明>".
接受风险 / 不采纳的处置也要复核其理由是否成立 -- 复核人可以推翻, 推翻后处置列改回 "待修".
全部复核通过后状态置 fixed, 结论改为最终值 (BLOCK -> OK with notes 等).
