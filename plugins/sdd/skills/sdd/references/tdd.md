# 实施阶段的 TDD

`/implement-cr` 的实施阶段按 red -> green 循环推进. 本文是循环的规则; 若环境里装了独立的
`tdd` skill (如 mattpocock-skills 的 `tdd`), 一并加载, 两者一致.

## 循环

1. **红**: 先写一个会失败的测试, 跑, 看它因为 "行为还没有" 而失败 (不是因为编译错 / 夹具错).
2. **绿**: 只写让这个测试通过的最少代码. 不为下一个测试预留, 不顺手加功能.
3. **下一片**: 回到 1. 重构不在循环里 -- 它属于 review 阶段 (03-impl 的车道 D).

一次一片 (vertical slice): 一个 seam, 一个测试, 一个最小实现. 不要先把 spec §5 的 T1..Tn
全写完再一起实现 -- 批量写出来的测试验证的是想象中的形状, 对真实变化不敏感, 而且在理解实现之前
就把测试结构定死了.

## 测试的来源: AC 与 spec §5

这套工作流里测试不用从零想: CR 变更内容表的每条 AC 就是一条测试的规格, spec §5 已经把它们编成
T1..Tn 并写明了夹具位置. 每片的顺序跟 spec §4 的步走: 步 1 的 T 先红后绿, 提交, 再步 2.

AC 写的是 "给定什么输入, 看到什么结果" -- 测试就按这个形状写, 名字用 AC 的语言
(`ReleasesEveryReturnedLevel`, 不是 `TestForceClearBranch2`).

## seam: 在哪测

seam 是能观察到行为而不必伸进内部的公共边界. 这个仓库的惯例:

- 真库集成测试 (`*_pg_test.go`, `pgtest.New(t)`), **不 mock 存储层**; provider 客户端按既有替身注入.
- seam 通常是: 服务方法 (确认事务, 处置循环的一轮), worker 的一轮 (`ProcessNextDisposition`),
  admin / customer handler, 迁移的 up / down.
- 只在系统边界 mock: 第三方 API, 时间, 随机. 自己的包, 内部协作者, 查询函数不 mock.

写测试前先列出这一步要测的 seam (spec §5 里已经写了的直接用); spec 没写的 seam 是范围外或
遗漏, 先补进 spec §9 再写.

## 反模式 (review 车道 E 会查)

- **耦合实现**: mock 内部协作者, 测私有函数, 断言调用次数 / 顺序, 或绕过接口去查库核对
  (要通过接口读回来核对). 特征: 重构后行为没变测试却红了.
- **同义反复**: 期望值用和被测代码一样的方法算出来 (`expect(total).toBe(items.reduce(...))`),
  于是永远通过. 期望值必须来自独立来源: 算例的字面量, spec §4 的算式手算结果, AC 里的数字.
- **同一事务测并发**: `first.tx == second.tx` 时第二次 advisory lock 是空操作, 测不出跨连接互斥.
  并发 / 幂等断言用两个连接.
- **只测正例**: AC 的负例 (非法配置被拒, NULL 语义, 未知结果不重发) 各要一条.
- **测试通过但没测到 AC**: 断言的是中间变量不是 AC 说的可观察结果.

## 每步结束

- 该步的 T 全绿, 且回归套件 (spec §5 列的) 绿.
- 一个提交. 提交信息引用 CR 与步号 (如 `CR-005 step 2: ...`).
- spec §4 落点列填提交 hash. 与计划不同的地方写进 §9.
