# /draft: 想清楚再立 CR

草稿是思考的容器, 不是交付物. 它存在的理由只有一个: 让后面的 REQ / CR 建立在读过代码的事实上,
而不是建立在会话里的印象上. 所以草稿允许不完整, 但 "现状" 一节的每条都要有 file:line.

## 步骤

1. **定位与约定**. 找到与本 skill 同级的 `sdd/scripts/sdd.py` (相对本文件 `../sdd/scripts/sdd.py`),
   读约定 `../sdd/references/conventions.md`. `docs/sdd` 不存在
   时问用户是否 `sdd.py init`, 不要自行建目录.
2. **定 slug**. 业务已有 REQ / CR 的, 复用它们文件名里的 slug (`sdd.py status` 能看到); 新业务取
   小写短横线名. slug 是草稿目录和将来 CR 目录的钥匙, 一致才能自动并入.
3. **只读侦察**. 读相关 REQ / CR 全文 (从磁盘重读, 不用记忆), 再读代码: 入口, 判定, 约束,
   队列 / 锁, 测试. 每个 "现在系统是 X" 都落到 file:line. 读的时候留意用户的问题有没有因为
   事实而变形 -- 常见的是 "想改 A" 读完发现瓶颈在 B.
4. **当思考伙伴, 不当流程**. 提问题, 挑假设, 摆多个方向让用户选, 用表格比选项, 给倾向但不硬选.
   用户在探索时不要催他立 CR.
5. **结论成形或用户要求时落盘**: `python3 ../sdd/scripts/sdd.py new-draft <slug> <topic>`,
   按模板 (`../sdd/assets/templates/draft.md`) 填: 问题 / 现状 (file:line) / 选项与取舍 / 倾向 /
   待定 (谁拍板) / 下一步. 一次会话可以有多份草稿, 文件名带日期不会撞.
6. **收尾给方向**: 业务没有 REQ -> `/req <slug>`; 有 REQ 要改行为 -> `/create-cr <slug>`;
   还没想清楚 -> 下次继续, 草稿在.

## 不做

- 不写、不改项目代码, 也不建 REQ / CR (那是 `/req` `/create-cr` 的事, 各有自己的模板和校验).
- 不把实现步骤写进草稿 (spec 的事), 不把规范条款写进草稿 (REQ 的事).
- 现状一节不写没核实的话. 拿不准就写 "未核实" 并列为待定.
