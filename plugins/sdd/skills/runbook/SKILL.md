# /runbook: 按环境、按批次的上线手册

上线文件 (`release/<批次>/`) 写的是 **"这一批要做什么"**, 对每个环境都成立. 到了某个环境, 要的是另一样
东西: 按什么顺序做、每步怎么先查、做到哪了、出了什么事. 这就是 runbook, 一个环境一批一份:

```
docs/sdd/release/runbook/<环境>/<批次>/
├── runbook.md   手册: 按执行顺序的步骤 + 每步状态. 干净可复用, 不写过程
├── log.md       执行记录: 时间 (UTC), 命令, 输出, 问题. append-only
├── sql/         这个环境要跑的 SQL 副本, 参数已填成这个环境的值
└── scripts/     这个环境要跑的脚本, 连同它依赖的辅助库, 都是副本
```

两份文件分工是这个 skill 的核心: **手册保持干净** (下一次在这个环境重演、或者照着去下一个环境, 拿来
就能用), **过程与问题按时间进 log** (排查时要的是 "当时发生了什么", 不是整理过的结论). 一个动作的
正文只在一处: 手册写 "做什么、怎么做", log 写 "做了、结果如何", 上线文件里各环境那一行只指过来.

## 参数与模式

`/runbook pre|run|auto <环境> <批次>`, 例 `/runbook pre ibnk-test sprint7`.

- **环境**: 项目里的名字 (ibnk-test, sandbox, prod ...), 不写死. 从 `release/runbook/` 下已有的目录与
  用户的话里取; 用户说 "沙箱" 而目录叫 `sandbox` 就用目录名. 新环境第一次出现时, 跟用户确认目录名.
- **批次**: `release/` 下的批次目录 (例 `sprint7`). 没给: 只有一个批次就用它, 否则列出来问.
- **模式**没给时按用户的话判: "写 / 补 / 更新手册" -> pre; "跑 / 上线 / 演练 / 接着做" -> run
  (手册还不存在就走 auto: 先 pre, 给用户过目, 再 run); "补跑回填 / 一次性程序", "记进手册",
  "这是环境问题吗" 见后面 "单点请求".

开工前: 定位 `../sdd/scripts/sdd.py`, 读约定 `../sdd/references/conventions.md` 的 "上线手册: release/runbook/"
一节; 模板在 `../sdd/assets/templates/runbook.md` 与 `log.md`.

## 硬规则: 环境目录自包含, 不引用

某个环境执行时要用的 SQL、脚本、脚本依赖的辅助库, **一律复制进 `release/runbook/<环境>/<批次>/`**
(`sql/`, `scripts/`). runbook.md 的每一步只指向这个目录里的文件, **不得引用** `release/<批次>/` 原件、
`archive/`、别的环境目录、会话草稿目录 (`draft/`, `work/`, `/tmp` 之类) 里的文件.

为什么: 原件会改 (实施中途补一条 WHERE), archive 会搬, 草稿会删, 别的环境填的是别的参数 -- 手册
指过去的东西一变, 你在这个环境 "照手册跑" 的就不是你核过的那一份了. 自包含的目录才能回答 "这个环境
当时跑的到底是什么".

- **一个环境一份副本**: ibnk-test 用的放 `release/runbook/ibnk-test/sprint7/`; 沙箱同一份 SQL 也复制一份
  到 `release/runbook/sandbox/sprint7/sql/`, 各自填各自环境的参数. 不跨环境共用.
- **副本头部写来源**: 原件路径 (相对 docs/sdd) + 复制时的 commit (docs/sdd 所在仓库的短 hash; 不是
  git 仓库就写日期) + 日期, 以及本环境填了哪些参数. 例:

  ```sql
  -- 来源: release/sprint7/CR-077-payout-schema-blocks.seed.sql @ a1b2c3d (2026-10-25)
  -- 本环境: ibnk-test; 参数: :tenant_id = 3 (见 log.md 第 2 条的只读核查)
  ```

  脚本用 `#` 注释写同样两行.
- **辅助库也复制**: 脚本 import 的辅助模块 (例 archive 里某个 `ibnk_admin.py`) 复制进同一个 `scripts/`,
  去掉指向别处的 `sys.path.insert(...)`, 改成同目录导入 (`python3 scripts/x.py` 运行时脚本所在目录本来
  就在 `sys.path` 上). 复制的辅助库同样写来源头.
- **原件改了要比对**: pre 重跑时, 对每份副本按头部的来源比对原件 (`git -C docs/sdd diff <commit> HEAD --
  <原件>`; 不是 git 仓库就直接 diff 原件与副本正文). 有变化的列给用户: 对应步骤**未完成**的, 更新副本
  并改头部 commit; **已完成**的不动 -- 那份副本是当时跑过什么的证据, 原件后来的修改若这个环境也要补,
  作为新步骤增补.
- **不写密钥值**: 副本、手册、log 里只写变量名与 "值见 `_secret/...`" 或 "读环境变量 X". 脚本从环境或
  `_secret/` 读值.

## pre: 写手册, 收集文档与脚本

不执行任何写操作. 可以对环境做**只读**核查 (SELECT, `kubectl get`, 读配置, 调只读接口) 来判 "已做 / 未做".

1. **建骨架**: `sdd.py new-runbook <环境> <批次>` (已有的 runbook.md / log.md 不动), 它顺带列出
   `release/<批次>/` 下的上线文件.
2. **核批次**: `sdd.py validate` 里有关 release 批次的警告 (文件不在 `release/<批次>/` 下, CR 没填
   `release:`) 先告诉用户 -- 落在批次目录外的上线文件会被这一步漏掉.
3. **读全部上线文件** (从磁盘逐份读, 不凭记忆): `CR-*.md` 与没有 CR 的工单文件 (`IB-*.md` 之类) 的
   "上线操作" / Manual SQL / go-live checks 各节, 以及 `*.sql` (seed, 核查, 回填), 一次性程序, 开关,
   管理端动作, mock 变更. 每个动作记下来源 (文件 + 节).
4. **读这个环境已有的记录**: log.md 全文 (哪些做过, 遇到过什么), runbook.md (重跑时).
5. **只读核环境现状** (能核就核): 当前部署的 commit、迁移号填进两份文件头; 每个候选步骤跑它的只读
   检查, 已经做过的标已完成. 核查本身是过程, 按 log.md 模板追加 "执行" 条目 (命令 + 结果), 手册里的状态
   写 `已完成 (log.md 第 N 条)`.
6. **排顺序**: 迁移 -> 配置 -> seed / 一次性程序 -> 开关 -> 验证. 同一类里按上线文件写明的先后约束
   (迁移之后、滚动容器之前、开关打开之前 ...); 约束互相冲突的写出来问用户, 不自己挑.
7. **写每一步** (模板第 2 节的六项): 来源 (CR / 工单编号 + 节, 只作出处, 不写原件路径)、做什么、执行前怎么检查 (只读)、具体命令
   或 `sql/` `scripts/` 里的文件、预期结果、失败怎么办、状态 (待做 / 已完成 / 不适用 + 原因).
   不适用于这个环境的动作 (生产专有, 这个环境没有那个渠道 ...) 列进第 3 节, 写原因; 整份不适用的上线
   文件在第 0 节标出.
8. **复制 SQL 与脚本** 进 `sql/` `scripts/` (照上面的硬规则: 来源头, 辅助库同目录, 参数填成这个环境的值).
   参数拿不准的写 `<待定: 谁给 / 怎么查>`, 列进给用户的问题里, 不猜.
   **要运营 / 供应商商务 / 产品合规提供或拍板的** (负责人与权限、收件人、开放清单、费率与阈值取值、门户里才有的
   key / IP 登记 / 预充值、后台审批): 不写进手册正文, 收进 `release/<批次>/ops/<主题>.md` (没有就建, 并在
   `ops/README.md` 登记, 状态 "待发"), 手册那一步状态写 `等运营 (见 ops/<主题>.md 第 N 项)`. 见 sdd conventions
   "留给运营处理的".
9. **重跑 pre 是增补**: 新步骤插进合适位置 (编号不重排, 用 `3a`; log.md 按编号引用), 改状态, 已完成的
   步骤不删; 比对副本原件 (见上).
10. **给用户过目**: 报步骤总表 (几步待做 / 已完成 / 不适用 / 等运营)、不适用清单与原因、待定参数、原件变了的副本、
    新写进 `ops/` 的待运营事项.
    停在这里, 不执行.

## run: 执行手册

1. **从磁盘重读** runbook.md 与 log.md, 找**第一个**状态不是 "已完成 / 不适用" 的步骤开始. 中断后再 run
   就是从这里接着做 -- 状态在文件里, 不在会话记忆里. 状态是 "阻塞" 的步骤先重跑它的只读检查, 问题已经
   解除就照常做, 否则跳过, 做后面不依赖它的步骤.
2. **每一步**:
   1. 跑这一步的只读检查. 显示已经做过 -> 标已完成, log 记一条 "检查显示已做", 下一步.
   2. 写库 / 跑一次性程序 / 改开关 / 改外部系统 (管理端、第三方控制台、mock) **先问用户**, 说清要执行的
      命令与预期影响. 用户这次明说 "都做" 的除外 -- 那句话只覆盖这一次 run 的这个环境、这个批次.
   3. 执行, 用的是本目录 `sql/` `scripts/` 里的副本.
   4. 对照预期结果核对 (跑后核对查询、输出最后一行、影响行数).
   5. **当场记两处**: runbook.md 这一步标 `已完成 (log.md 第 N 条)`; log.md 追加 时间 (UTC)、命令、
      输出最后一行、影响行数. 一步一记, 不攒到最后 -- 中途断了, 下次 run 靠它接上.
3. **遇到问题**: log.md 记一条 "问题": 现象 -> 怎么核查 -> 怎么处理 -> 结果. 先判是哪一类:
   - **环境问题** (缺配置、mock 不像、种子没跑、权限、网络、外部系统没开通): 直接修 (修复本身是写操作的,
     照 2.2 先问), 记进 log; 修复要以后在别的环境也做的, 增补成手册的一个步骤.
   - **代码问题** (同样的输入在代码层面行为不对, 与 REQ / CR 不符): **不在这里修**, log 里只记一句指向
     工单 / CR, 该步标 `阻塞: 见 log.md 第 N 条`; 后面不依赖它的步骤继续做, 依赖它的停下来问.
   - 判据: 换个环境同样的代码正常吗? 报错发生在读配置 / 调外部依赖, 还是业务断言? 代码路径与 REQ / CR
     写的一致吗? 拿不准就把判断依据摆给用户问, 不硬归类.
4. **收尾**: 报完成几步、阻塞几步 (各指向哪个工单 / CR)、还剩几步, 以及这次修过的环境问题.

## auto

先 pre, 写完**同样先给用户过目**, 用户确认后再 run. 过目这一步不因为是 auto 就省.

## 单点请求

- **"补跑回填 / 一次性程序"**: 找到手册里对应的步骤 (没有就先按 pre 的规则增补一步, 连同副本), 照 run
  的单步流程做: 只读检查 -> 问 -> 执行 -> 核对 -> 两处记.
- **"记进手册"**: 用户在环境上自己做了事. 追加 log.md 条目 (问清命令与结果); 对应手册某步的改状态,
  手册里没有而以后还要做的增补成步骤.
- **"这是环境问题吗"**: 按 run 第 3 步的判据核 (只读), 给出判断与依据, 记进 log.md 的 "问题" 条目.

## 不做

- 不改项目代码; 代码问题只指向工单 / CR.
- pre 不执行写操作; run 的写操作不跳过询问 (除非用户这次明说 "都做").
- 不引用环境目录以外的文件; 不写密钥值.
- 不改、不删 log.md 已有条目 (写错了追加更正); 不删 runbook.md 里已完成的步骤.
