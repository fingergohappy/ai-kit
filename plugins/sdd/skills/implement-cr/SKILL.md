# /implement-cr: 做下一件事

这个命令不是一条直线, 是一个由状态驱动的循环. 先看状态, 再决定做哪一段; **一段**做完停在一个
可 review 的点上. 为什么: 写 spec 之前要审文档, 写代码之前要审计划, 落实之前要审实现 --
每一段都是独立会话也能接上的.

**"段" 是下面的 R / A / B / C 四段, 不是 spec §4 的 "步"**. 段 B 内部有多少步就连着做多少步,
步与步之间不停也不提交 -- 一步的 T 绿了就汇报一句做到哪, 直接开始下一步, 不等用户说 "继续";
回归、提交、填落点、跑 status 都在段 B 收尾做一次. 停在段的边界上是因为那里要 review; 步的边界上
没有 review, 停在那里只是把活干了一半.

## 第 0 步: 看状态

1. 定位 `../sdd/scripts/sdd.py`; 读约定 `../sdd/references/conventions.md`.
2. `python3 ../sdd/scripts/sdd.py status CR-NNN`. 没给 CR 编号: 会话里提过就用那个, 只有一个
   未 fixed 的 CR 就用它, 否则列出来问. 宣布 "处理 CR-NNN", 说明可换.
3. 从磁盘重读 CR 全文与影响的 REQ (用户可能在会话中间改过).
4. CR 状态是 `to fix` 就改成 `fixing` (frontmatter 的 `status`).
5. 按 "下一步" 进入下面某一段. 下一步指向 `/review-cr` 时, 说明原因并停 -- 除非用户明确说
   "跳过 review". 跳过要记进 spec §9.
   **用户说过 "推进到 X" / "一路做到 X" / "别问我" 就不停**: 那句话是授权, 照 `../review-cr/SKILL.md`
   把那次 review 做掉 (并行还是串行读 `.parallel`), 回来重读状态继续下一段 -- 这就是 `/auto-cr`
   的主循环, 只是起点不同, 轮次上限与停止条件一并照它那两节. 越权四项仍然必停.

## 段 R: 有 review 发现未处置

对每条处置列为 "待修" 的发现 (按 P0 -> P2):

- 修: 改代码 / 文档. **这一轮的修复合成一个提交** (P0 可单独一个), 处置列各条填同一个 hash --
  逐条一提交会让一个 CR 堆出十几个 `fix:`. 提交信息一句话说清修了什么, 不写编号.
- 不修: `接受风险: <理由>` 或 `不采纳: <理由>`. 理由要能让复核人判断, 不写 "影响不大".
- 发现指出的是 spec / CR / REQ 的错误, 就改那份文档, 处置写 `修复 (spec §1.4)` 之类.
- **发现与 CR 里已和用户确认的逻辑冲突**: 以 CR 为准, 不改代码, 处置写
  `不采纳: CR 第 N 节已确认 <那条决策>`. 审的人读不到你和用户的讨论, 不等于那个决策没发生过.

全部有处置后 review 状态置 `fixing` (不是 fixed -- fixed 由复核给), 提示 `/review-cr CR-NNN <stage>`
复核. 处置期间发现新的问题, 追加新编号的发现行, 不改旧行.

## 段 A: 没有 spec -> 交给 /spec

写实施 spec 是只读工作 (侦察 + 计划), 不在本命令里做 -- 那条边界让用户可以只要方案不要改动.
告诉用户下一步是 `/spec CR-NNN`, 停在这里. 本命令从 spec 写好并审过之后接手.

## 段 B: spec 审过, 有待办步骤 -> 实施

前提: `02-spec` review 状态 fixed. 否则停 (软闸门).

开工前读 `docs/sdd/lessons.md` (有的话): 这个仓库真犯过的错, 按车道排; 本次改动涉及的车道里次数 >= 2 的
条目, 写代码时当作自检项 -- review 阶段一定会拿它们对照.

按 spec §4 的顺序实施. **步是顺序单元, 不是提交单元: 整段 B 做完提交一次**, 落点列各行填同一个
hash. 不要每做完一步就跑回归、提交一次 -- 十几步就是十几遍回归加十几条提交, 落到 main 上全是
噪音. 只有 spec §4 顺序约束里写明必须分批上线的 (迁移要先于代码单独发一版) 才按批拆提交;
拆也不能只做半步 -- 半步的中间状态不满足 §4 那条 "合并后系统仍然正确".
每一步内部按 TDD 走, 规则见 `../sdd/references/tdd.md`
(环境里装了 `tdd` skill 的一并加载), 要点:

- 这一步对应的 T (spec §5) 就是测试规格, T 又对应 AC. 先写让它红的测试, 再写最少的代码让它绿,
  再下一片. 不批量先写全部测试.
- **红的判定行抄进 spec §5 这条 T 的 "红:"** (失败断言那行输出). 这就是变异验证的证据, review
  车道 E 有记录的不再重打; 代码没写测试就绿的, 是测试没测到新行为, 改测试, 不往下写.
- 真库集成测试, 不 mock 存储层; 只在系统边界 mock. 并发 / 幂等断言用两个连接.
- 期望值来自独立来源 (算例字面量, AC 的数字), 不从被测逻辑推.
- 该步的 T 全绿就进下一步. 回归套件留到段 B 收尾跑一次, 不是每步跑.
- 与 spec 不一致的地方 (多改了一个文件, 顺序调换, 侦察漏了事实) 写进 §9, 当场写, 不攒.
- **这一步产生的上线事实当场记进 `release/CR-NNN-<slug>.md`** (与 cr/ 同级, 不在工作目录里, 提炼时不会被删): 迁移号与它锁不锁表 / 上一版
  binary 能不能跑新 schema, 新环境变量, 新的运行时配置键, 跑过的验证命令与它最后一行输出.
  这份文件 `/spec` 时脚本已经建好了, **它就是项目自己那份 PR 模板的整份副本** -- `sdd.py`
  优先找 `.github/pull_request_template.md` (GitHub 认的位置, 网页开 PR 弹的就是它), 找不到
  才退到通用六项. 所以**不要另搭骨架, 照它现成的节填空**: 每节顶上的 HTML 注释写着这一节的
  事实该去哪里核, 照着做. **正文用中文写** (模板是英文的, 照英文骨架填空容易顺手写成英文;
  节标题、表头、检查项题头保留模板原文, 命令输出、错误文本、标识符、hash 逐字不动).
  开 PR 时 `ship-pr` 把它翻成英文整份贴进正文 -- PR 正文是英文的, 这份文件是中文的事实来源 --
  贴之前把 HTML 注释和没替换的占位符删干净.
  脚本只认确定的路径. 项目 CLAUDE.md / AGENTS.md 用自然语言指了别处的模板时, 自己去看一眼,
  以那份为准 -- 那种指法脚本读不出来.
  当场记的理由和 §9 一样: "上一版 binary 能不能跑新 schema" 与验证命令的输出, 三次 review
  走完再回忆就只能靠猜.
- **要人手跑的 SQL 落到 spec §3 判好的那个位置, 不要临时改主意**: 参考数据写进迁移文件,
  环境配置写进项目里入库的 seed 脚本, 只有跑完即弃的一次性回填才 `sdd.py new-seed CR-NNN [名字]`
  建到 `release/CR-NNN-<slug>.seed[-<名字>].sql` (与上线产物并排), 按模板头部填齐归宿, 时机, 幂等性, 预估行数,
  回退, 正文按 "跑前核对 -> 幂等正文 -> 跑后核对" 三段写. **SQL 全文只存在于那一个文件**:
  上线产物那一节只写指路与事实 (哪个文件, 什么时候跑, 跑过没有, 影响了多少行), 贴两份必漂移,
  而跑的人只该有一个来源. 真跑过之后当场把文件头的 `env= date= rows= by=` 填上 --
  `sdd.py prune` 认这一行, 空着就不许删 (`status` 也会把它列成未执行).

停下来问, 不默默吸收 (借 OpenSpec apply 的规则):
- 步骤不清, 或实现揭示 spec / CR 的设计有问题.
- 做下去需要放宽、跳过、推迟某条 AC, 或改 §7 说不做的东西 -- 这是范围变化, 由人决定.
- 遇到 spec 没预见的阻塞 (迁移冲突, 守卫红).

**但用户说过 "推进到 X" / "一路做到 X" / "别问我" 就别停**: 那句话是授权, 上面这几条改成
"按推荐做法执行 + 记 OQ 往下走" (照 `../sdd/references/conventions.md` 的
`## 业务决策: 谁拍板, 什么时候问`). 越权那四项仍然必停, 授权也盖不住.

**"剩下那几步更重" 不是停的理由.** 段 B 的边界是 §4 的步**全部**落地, 不是 "这一步做完了".
下一步要新写一个 worker、加三条查询、补十个测试 -- 那也是这一段的活, 接着做, 不要在这里问
"要我继续往下做吗". 该停的只有上面那三条 (步骤不清 / 范围变化 / 没预见的阻塞), 与剩下多少活无关;
这一条不看有没有授权, 做完整段本来就是这次调用的职责.

每步做完汇报一行 -- "步 N/M 做完, 接着步 N+1", 让用户知道做到哪了. 那是**汇报**, 不是在征求
同意, 说完直接开始下一步. 中途不跑 `sdd.py status`: 落点没填 hash 之前那张八关表不会变, 它记的
是流程走到哪关, 不是 spec 做到哪步.

**段 B 收尾** (全部步落地后, 一次做完):
- 跑 spec §5 全部回归, 全绿才提交.
- 提交一次, 提交信息按 `../sdd/references/tdd.md` "段 B 收尾" 那节写. 落点列各行填这个 hash.
- `sdd.py status CR-NNN --write` 贴进度, 提示 `/review-cr CR-NNN impl`.

## 段 C: impl 审过 -> 落实

前提: 三次 review 都 fixed. 同一个提交里完成:

1. **更新 REQ 到新结论**. 按 CR 变更内容表逐条改正文: 条目号沿用, 删除的保留编号标 "已删除,
   见 CR-NNN", 新增的续编. 通读一遍 -- 不是只改表里列的行: 目标 / 非目标 / 5.2 时序图 / 第 6 节 /
   第 8 节里被牵连的措辞一并对齐 (点状打补丁漏改是最常见的失败). §11 代码落点更新.
   状态: draft 的置 implemented; 最后更新日期改.
   变更记录追加一行: 日期, CR-NNN, 摘要; 结论来源是 review 的写编号 (`CR-NNN I-3`).
   REQ 正文只写结论: 推导与复现留在 review, 不搬.
2. **CR 第 5 节落实**填全: spec 路径, 三次 review 的状态与结论, 实现提交, REQ 更新提交, 备注
   (未随本次合入的待办写清). 状态置 `fixed`.
3. `sdd.py validate` 必须 0 错误; `sdd.py index`.
4. 汇报: 改了哪些 REQ 条目, 提交列表, 遗留待办. 提示下一步 `/review-cr CR-NNN distill` -- 把三次 review 里
   犯过的错提炼进错题本, 再盘点工作目录并与用户确认后清理 (`sdd.py status CR-NNN` 也会指到这里).

## 不做

- 不写 spec (那是 `/spec`); 不改 `/review-cr` 该写的 review 结论 (处置列除外).
- 不跳过 review 闸门, 除非用户明确说. 不把 "待办" 换成勾.
- 不为了让测试通过而改测试的期望值; 期望值错了先回到 AC / spec §4 算式核对.
