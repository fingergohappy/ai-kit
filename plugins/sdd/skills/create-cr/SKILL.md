# /create-cr: 立一次工作单元

CR 是一次带来 REQ 变化的工作单元: spec 与三次 review 都挂在它的目录下. 它同时是审计轨迹 --
半年后有人问 "安全垫为什么从环境变量改成落库" 或 "当初为什么要做这个业务", 答案在这里, 不在 REQ 里.
所以动机要带出处, 否决的方案要留档.

两种形态, 第 2 步判断走哪个:

| 形态 | 何时 | 模板 | 第 1-3 节写什么 |
|---|---|---|---|
| **变更 CR** | 目标业务已有现行 REQ, 要改它的行为 | `cr.md` | 为什么原需求不再成立; 按条目号 "现行 -> 变更后"; 影响分析 |
| **立项 CR** | 全新业务, 还没有 REQ | `cr-new.md` (`new-cr --new`) | 为什么现在做; 本期交付范围; 对现有系统的影响 |

后续步骤 (spec, 三次 review, 落实) 两者完全一样.

## 步骤

1. **定位与约定**. `../sdd/scripts/sdd.py`; 读约定 `../sdd/references/conventions.md`; 读
   `../sdd/references/writing-guide.md` 的 "CR 变更内容表的一行".
2. **判断形态, 找目标 REQ**. `sdd.py status` 看这个业务有没有现行 REQ.

   - **有** (implemented): 变更形态. CR 必须挂在它的具体条目上 (FR-x / BR-y / AC-z).
   - **没有**: 新增形态. 先 `/req <slug>` 建一份描述**本期目标形态**的 REQ (状态 draft), 再回来立
     立项 CR. 注意 draft REQ 本来就可以随便改, 立项 CR 不是为了管控它, 是为了有个地方挂 spec 与
     review, 并记录 "为什么做, 交付到哪".
   - **有但还是 draft**: 说明上一次立项还没落实完. 别新建 CR, 接着做那个 (`sdd.py status CR-NNN`).

   任何一种都不立没有目标 REQ 的 CR.
3. **读草稿**. `docs/sdd/notcommit/<slug>/draft/` 有东西就全读 (从磁盘), 那是 `/draft` `/req` 留下的
   事实与选项. 没有草稿而改动不小 (跨表, 改状态机, 有资金含义) 时, 先做一轮只读侦察, 关键事实
   file:line 记到草稿 (`sdd.py new-draft <slug> cr-recon`), 再写 CR.
4. **核实 "现行"**. 变更内容表的 "现行" 列必须与 REQ 原文一致 (review 车道 B 逐字核), 并且
   与代码一致 (车道 A 核) -- REQ 与代码不一致的, 先在 CR 动机里说明, 不要以其中一方为准悄悄写.
5. **建文件**: 变更形态 `sdd.py new-cr <slug> "<标题>"`; 新增形态 `sdd.py new-cr <slug> "<标题>" --new`.
   脚本分配编号, 按形态选模板, 建 `notcommit/CR-NNN-<slug>/`, 并把 `notcommit/<slug>/` 草稿并进去.
6a. **变更形态按模板写** (`../sdd/assets/templates/cr.md`):
   - 影响需求精确到条目号, 用链接 `[REQ-006](../req/REQ-006-xxx.md) (FR-8, AC-8)`.
   - 变更内容: 一行一个条目, "现行 -> 变更后"; 新增标 "(新增)" 且新增 FR 必带新增 AC;
     删除写原因与存量处置; FR / BR 动了对应 AC 也列进来; 状态机变了贴新片段并改迁移表;
     写清 "不变的部分".
   - 影响分析五项逐个过 (同 REQ 其他条目 / 其他 REQ / API 与调用方 / 数据与迁移, 含预期内的
     中间态 / 在途与已上线行为).
   - 替代方案: 考虑过没采纳的, 带原因.
   - 落实一节留给 `/implement-cr`, 只填 spec 路径.
   - 摘要一句话 (进 INDEX).

6b. **新增形态按模板写** (`../sdd/assets/templates/cr-new.md`):
   - 立项需求指向刚建的 REQ, 通常写 `(全文)`.
   - 立项动机写 "为什么是现在" (REQ 第 1 节写的是 "这个业务解决什么问题", 不重复).
   - 交付范围默认就是 REQ 全文 -- REQ 只描述本期形态. 想好但不做的能力写进 REQ 非目标 (不编号),
     不要写成编号条目却不实现 (implemented 的 REQ 里未标注的条目即已实现, validate 会拦).
   - 对现有系统的影响是这份文档最容易漏也最值钱的一节: 依赖哪些现有 REQ 的行为, 会不会与现有
     worker / 队列 / 锁 / 路由 / 幂等键空间冲突, 共享表加约束会不会让现有写入失败, 开关怎么回退.
     这一节靠只读侦察得来 (第 3 步), 不靠推测.
   - 替代方案对新业务尤其重要 (选型自由度大), 别留空.
   - 摘要一句话 (进 INDEX).
7. **校验**: `sdd.py validate` (引用了 REQ 里不存在的条目会警告 -- 新增条目在表里标 "(新增" 即可),
   `sdd.py index`.
8. **定并行策略** (只问这一次, 三次 review 都沿用). 探测环境: `$TMUX` 非空, 且 `codex` / `pi`
   至少一个在 PATH 上. 两个都满足才问:

   > 这个 CR 的三次 review 可以按车道派给 codex / pi 并行审 (每阶段 1-5 个窗口, 看车道适用几条),
   > 也可以我自己串行审. 并行吗?

   把答案写进工作目录: `echo yes > <工作目录>/.parallel` (或 `no`). `/review-cr` 每次读它,
   不再问; 想改主意就改这个文件. 环境不满足**不要问**, 也不用写文件 -- `/review-cr` 读不到
   就按串行走, 那本来就是唯一可行的路. 怎么并行审见 `../review-cr/SKILL.md` 的 `## 并行审`.
9. **收尾**: 报文件路径、影响条目清单、并行还是串行, 下一步 `/review-cr CR-NNN docs`.

## 不做

- 不改代码, 不改 REQ 正文 (REQ 在 `/implement-cr` 落实阶段随代码一起更新, 保证文档与代码同一提交).
  新增形态也一样: REQ 由 `/req` 建好后就不在本命令里改.
- 不把实现步骤写进 CR (spec 的事); 不把 file:line 写进变更内容表 (草稿 / spec 的事).
- 范围有实质歧义 (影响可观察行为, 兼容性, 验收标准) 时问用户, 不猜; 小细节自行假设并写进 CR.
