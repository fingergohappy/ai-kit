# tmux_dispatch

把任务交给另一个 tmux pane 里的 agent，然后让开。

和 `tmux_reply` 成对使用才是重点。本 skill 只负责投递，不盯着对方的 pane 看，也不应该看——循环 `capture-pane` 只是把自己这一轮耗在一块只有对方能推进的屏幕上。取而代之的是：每个派出去的任务都盖着你的 pane id 和一句「用 tmux_reply 回报」。对方干完自己敲门，你这边这段时间是自由的。

## 确定 pane id

pane id 一律显式给出，来自 `$ARGUMENTS`（`%7 …`、`7 …`）或用户刚说的话（「让 7 去修这个」「发给 %3」）。纯数字视为 `%<数字>`。

如果哪儿都找不到 pane id，用纯文本询问——不要列出 pane 清单让用户挑。用户正看着自己的 tmux 布局，心里清楚指的是哪个 pane，生成的列表只是噪音；而猜比问更糟，因为猜错就是把任务丢进一个毫不相关的 session。

## 先把任务写清楚，再发送

这一步决定委派成不成，也是「派任务」和「发条命令」的根本区别。对方 agent 从零开始：看不到这边的对话、你打开的文件、你的 cwd，也看不到你刚刚得出的结论。凡是只有在**这边**才成立的指代，到了**那边**都变成谜题——而困惑的 agent 不会停下来，它会猜，然后自信地做错事。

所以把请求改写成一份自包含的任务书：

- **只用绝对路径。** 对方 pane 可能在别的目录，甚至同一个 repo 的另一个 worktree。
- **展开所有指代。** 「刚才那个函数」「上面那个报错」「我们改的那个文件」→ 真实路径、真实符号名、把报错原文贴进去。
- **写清「做完」长什么样**——该跑过的命令、该改变的行为。没有终点线，对方会自己发明一个，通常比你想要的更激进。
- **圈出别碰的地方**，如果这活紧挨着你不想动的东西。
- **保留你的不确定。** 如果你也不确定该改 A 还是 B，就说出来。把猜测说成事实，是小任务变成错误重构的典型路径。

同一个请求，单薄版 vs 自包含版：

单薄 —— `把刚才那个 token 的 bug 修一下`

自包含：

```
修复 /Users/me/proj/src/auth.ts 中 verifyToken 的过期判断。
当前写的是 `if (payload.exp < Date.now() / 1000)`，但本服务签发的 exp 是毫秒时间戳，
结果所有 token 一律被判为已过期。改成毫秒比较，并补一个单测覆盖「刚签发的 token 仍有效」。
验收：cd /Users/me/proj && npm test -- auth 全绿。
不要改动 refreshToken 的逻辑，那部分另有 issue 在跟。
```

第二版更长，而这个长度就是全部的增值所在。

## 脚本路径

所有 `scripts/` 路径相对于**本 SKILL.md 文件所在目录**。执行前必须先解析为绝对路径，因为插件可能装在缓存目录而不是仓库里：

```bash
SKILL_DIR="<本 SKILL.md 所在目录的绝对路径>"
```

## 发送

```bash
# 短任务，直接传内容
bash "$SKILL_DIR/scripts/dispatch.sh" "<pane_id>" "<任务>"

# 长任务或多行 —— 先写文件，传路径
bash "$SKILL_DIR/scripts/dispatch.sh" "<pane_id>" "/tmp/task.txt"

# 审查-修复循环：gate-review 可以自行重派修复，不用停下来问
bash "$SKILL_DIR/scripts/dispatch.sh" "<pane_id>" "/tmp/task.txt" --loop
```

只有用户希望审查-修复循环无人值守时才加 `--loop`——它就是授权 `gate-review` 不先请示就把修复任务发回去的那把钥匙。默认不加，因为一次错误的自动重派比问一句代价大得多。这个标志随戳一起传过去，由接收方在回报里带回来，这是它唯一能活过一个来回的方式。

任务一旦是多行、含反引号或引号，就优先用文件形式。它彻底绕开 shell 转义问题，而一份被转义搞乱的任务书远比一条报错的命令难被发现。

**必须且只能**通过脚本发送，绝不要直接用 `tmux send-keys` 发任务文本。脚本处理的正是那些会静默出错的地方：bracketed paste 让换行不会把任务切成碎片提交、Enter 单独发一次让 TUI agent 真的收到、盖上发送方 pane id 建立回报通道、校验失败即退出而不是把内容粘进当前活动 pane、防止派给自己、以及用完清理 buffer 不占用户的粘贴栈。

## 发送之后

汇报：派给了哪个 pane、一句话说明派出去的是什么、以及脚本打印的回执。然后就停下，去干别的。

在宣布成功之前先读回执。如果回执显示对方 agent 正在忙，你的任务是排在那件事后面而不是已经开始——要说清楚，因为「已派出」和「正在做」是两个不同的说法。如果回执显示的是 shell 提示符或一个不相关的程序，任务很可能落错了 pane，立刻指出来，不要报成一次干净的交接。

等回报最终到达你的 pane 时，把它当成要转述给用户的报告，而不是一条需要回复的消息。只有确实有新活时才再派一次。
