# tmux-dispatch

给另一个 tmux pane 里的 agent 留一份文档，把活交出去，然后让开。

底下所有内容都由两条规则决定。

**文档才是消息本身。** 任务写进 `docs/tmux-channel/` 下的一个文件，通过 tmux 传过去的只有它的绝对路径，别的什么都不传。粘过去的任务正文只活在对方 pane 的 scrollback 里——对方一压缩上下文就再也读不到，你验收时也没法把它原样引回来，换行落错位置还会被切成碎片。文档能扛住这些，而且事后两个 agent 可以指着同一段文字精确地争论。

**投完就停。** 本 skill 不盯着对方的 pane 看，也不应该看——循环 `capture-pane` 只是把自己这一轮耗在一块只有对方能推进的屏幕上。每次派发都盖着你的 pane id 和一句「把报告追加回同一份文档，再用一行以 `DONE:` / `BLOCKED:` / `QUESTION:` 开头的状态敲门」。那一行就是唤醒你的东西：结论不用打开任何文件就能知道，只有需要证据时才去翻文档。对方干完自己敲门，你这边这段时间是自由的。

## 确定 pane id

pane id 一律显式给出，来自 `$ARGUMENTS`（`%7 …`、`7 …`）或用户刚说的话（「让 7 去修这个」「发给 %3」）。纯数字视为 `%<数字>`。

如果哪儿都找不到 pane id，用纯文本询问——不要列出 pane 清单让用户挑。用户正看着自己的 tmux 布局，心里清楚指的是哪个 pane，生成的列表只是噪音；而猜比问更糟，因为猜错就是把任务丢进一个毫不相关的 session。

## 通信频道

频道是这个活所属项目根目录下的 `docs/tmux-channel/`——用 `git rev-parse --show-toplevel` 取根目录，取不到就用 cwd。目录不存在就先建。

一次往返一份文档，命名 `<YYYYMMDD-HHMM>-<slug>.md`，而且只追加不改写：任务、回报、追问、再回报全都堆在同一个文件里，事后从头读到尾就是完整的一趟。

```markdown
# 修复 verifyToken 的过期判断

- panes: %5 → %7
- repo: /Users/me/proj

## Task — %5 → %7 — 2026-04-26 19:30

<任务书>

## Report — %7 → %5 — 2026-04-26 20:05

DONE: <接收方追加：第一行是状态，证据写在它下面>
```

`## Task` / `## Report` / `## Follow-up` 这几个标题是协议，不是排版：`reply.sh` 会检查文档最后一节是不是 Report，不是就拒绝敲门——正是这一条挡住了「活说做完了却什么都没写下来」。标题必须保持上面的英文原样（两端脚本按它校验），正文用什么语言都行。

如果任务已经有现成文档——`agentflow:task` 生成在 `docs/tasks/` 下的任务书、一份 spec、一份 review 报告——不要直接派那个文件。另写一份频道文档链接过去，再补上这次交接特有的东西，让报告落进频道，而不是去改一份别人在维护的文档。

## 先把任务写清楚，再发送

这一步决定委派成不成，也是「派任务」和「发条命令」的根本区别。对方 agent 从零开始：看不到这边的对话、你打开的文件、你的 cwd，也看不到你刚刚得出的结论。凡是只有在**这边**才成立的指代，到了**那边**都变成谜题——而困惑的 agent 不会停下来，它会猜，然后自信地做错事。

所以 `## Task` 一节要写成一份自包含的任务书：

- **只用绝对路径。** 对方 pane 可能在别的目录，甚至同一个 repo 的另一个 worktree——同一个相对路径在那边是另一个文件。
- **展开所有指代。** 「刚才那个函数」「上面那个报错」「我们改的那个文件」→ 真实路径、真实符号名、把报错原文贴进去。
- **写清「做完」长什么样**——该跑过的命令、该改变的行为。没有终点线，对方会自己发明一个，通常比你想要的更激进。
- **圈出别碰的地方**，如果这活紧挨着你不想动的东西。
- **保留你的不确定。** 如果你也不确定该改 A 还是 B，就说出来。把猜测说成事实，是小任务变成错误重构的典型路径。

同一个请求，单薄版 vs 自包含版：

单薄 —— `把刚才那个 token 的 bug 修一下`

自包含，写成 `docs/tmux-channel/20260426-1930-fix-verify-token.md`：

```markdown
# 修复 verifyToken 的过期判断

- panes: %5 → %7
- repo: /Users/me/proj

## Task — %5 → %7 — 2026-04-26 19:30

修复 /Users/me/proj/src/auth.ts 中 verifyToken 的过期判断。
当前写的是 `if (payload.exp < Date.now() / 1000)`，但本服务签发的 exp 是毫秒时间戳，
结果所有 token 一律被判为已过期。改成毫秒比较，并补一个单测覆盖「刚签发的 token 仍有效」。
验收：cd /Users/me/proj && npm test -- auth 全绿。
不要改动 refreshToken 的逻辑，那部分另有 issue 在跟。
```

第二版更长，而这个长度就是全部的增值所在。

## 脚本路径

所有 `scripts/` 路径相对于**本 SKILL.md 文件所在目录**。执行前必须先解析为绝对路径，因为插件可能装在缓存目录而不是仓库里：

```bash
SKILL_DIR="<本 SKILL.md 所在目录的绝对路径>"
```

## 发送

```bash
bash "$SKILL_DIR/scripts/dispatch.sh" "<pane_id>" "docs/tmux-channel/<名字>.md" "<一句话摘要>"
```

摘要可选，也是唯一跟着路径一起过去的正文——一行，够对方认出这是什么任务就行，不承载任何要执行的内容。脚本会把换行压掉并截断，所以别想用它夹带任务书；对方需要的一切都写进文档。

**必须且只能**通过脚本发送，绝不要直接用 `tmux send-keys` 发任务正文。脚本处理的正是那些会静默出错的地方：不是现成文档的文本直接拒收、把相对路径解析成绝对路径以免在对方 cwd 下指向另一个文件、文档不在频道目录下时告警、bracketed paste 让指针消息不被切成碎片提交、Enter 单独发一次让 TUI agent 真的收到、盖上发送方 pane id 建立回报通道、防止派给自己、以及用完清理 buffer 不占用户的粘贴栈。

## 发送之后

汇报：派给了哪个 pane、频道文档路径、一句话说明派出去的是什么、以及脚本打印的回执。然后就停下，去干别的。

在宣布成功之前先读回执。如果回执显示对方 agent 正在忙，你的任务是排在那件事后面而不是已经开始——要说清楚，因为「已派出」和「正在做」是两个不同的说法。如果回执显示的是 shell 提示符或一个不相关的程序，指针很可能落错了 pane，立刻指出来，不要报成一次干净的交接。

## 回报到达时

它是两行：一行状态，加同一份文档的路径。

```
BLOCKED: refreshToken 也有秒/毫秒混用，需要你决定是否一并改
Report in: /Users/me/proj/docs/tmux-channel/20260426-1930-fix-verify-token.md
```

状态决定你的下一步，而这三种是真的不一样：`DONE:` 说明这趟往返可以收了，`BLOCKED:` 说明活卡住了、要你动一下才能继续，`QUESTION:` 说明对方在等你欠它的那个回答。按这一行行动——不要为了搞清是哪一种而先去开文档。

但在转述之前，一定要读 `## Report` 一节。状态只是标题；用户可能会去核对的证据——跑了什么命令、真实输出、对方跳过了什么——在文件里，而且就压在该被对照的任务书下面。只转述状态，等于替一个你没看过的说法背书。

把回报当成要转述的报告，而不是一条需要回复的消息。只有状态要求你动时才回：回答 `QUESTION:`、或解开 `BLOCKED:`——把内容作为 `## Follow-up` 追加进同一份文档，再把路径发一次。`DONE:` 什么都不用回，一句「收到」只会在那边平白开启新的一轮。
